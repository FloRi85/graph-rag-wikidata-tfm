# Reproducing the thesis results

This guide accompanies the final thesis, submitted separately as a PDF. It is
a submission-time map of the retained evidence, not a new pre-registration.
The public repository is a single snapshot; dated run metadata preserves the
earlier experiment settings and provenance.

## Start with stored outputs

Use Python 3.11.9 and the pinned dependencies for exact report reproduction.
Newer runtimes may differ at floating-point precision without changing printed tables.
Install the dependencies as described in the root README. The commands below
assume the virtual environment is active. In PowerShell, activate it with
`.\venv\Scripts\Activate.ps1`; alternatively replace `python` with
`.\venv\Scripts\python.exe` in each command. On Linux/macOS use
`source venv/bin/activate`. No API key or model
download is required for answer re-scoring, the stored-score analyses or the
metric-report check. Restore the sealed answer file using
[the test-run instructions](../data/results/test_runs/README.md), then run from
the repository root:

```powershell
$testDir = 'data/results/test_runs/20260819_2017_nvidia-llama-3-3-nemotron-super-49b-v1_mintaka_test_raw'
$testRaw = Join-Path $testDir '20260819_2017_mintaka_test_raw_raw.json'
$devDir = 'data/results/dev_runs/20260818_1113_nvidia-llama-3-3-nemotron-super-49b-v1_reference-v8'
$devRaw = Join-Path $devDir '20260818_1113_reference-v8_raw.json'

python tools/report.py $testRaw
python tools/report.py $testRaw --baseline rag
python tools/report.py $testRaw --baseline graph_rag
python tools/report.py $devRaw
python tools/build_metric_reports.py --check
```

`report.py` regenerates the statistical JSON for its input and baseline; it
does not alter the raw answers. `build_metric_reports.py --check` regenerates
the deterministic supplement outputs in memory and compares them with the
saved files, without writing files. The timestamped manifest is excluded
from this comparison.
Do not replace the archived run metadata merely to make historical code
hashes match this submission snapshot.

## Result-to-instrument map

The following commands use stored evidence only. JSON-producing commands may
replace their derived analysis file, but do not generate new answers or judge
scores. Run in a working copy if the original derived-file bytes must stay
unchanged.

| Thesis evidence | Command or retained source |
|---|---|
| Overall outcomes, threshold sensitivity, baseline comparisons, F1 on selected and jointly attempted sets | `python tools/report.py $testRaw`; repeat with `--baseline rag` for C3/C4 against C2 and `--baseline graph_rag` for C4 against C3. |
| Answer-type, complexity and topic tables; six configuration pairs; full versus attempted populations | `python tools/build_metric_reports.py --check`; inspect `data/analysis/test4000_metric_reports/`. |
| Context medians and means | `python tools/compare_context_sizes.py --before $testDir --after $testDir --out output/context_sizes.json`. The same-directory arguments request within-run summaries, not an experimental before/after effect. |
| Gold-form presence; form lost or newly detected after condensing | `python tools/context_gold_coverage.py $testRaw`. |
| Hallucination by complexity, category and gold-form presence | `python tools/stratified_claim_checks.py $testRaw`. Reads the coverage JSON generated by the preceding command. |
| Mean faithfulness, common-scoreable pairs and correct-versus-hallucinated answers | `python tools/compare_faithfulness.py data/analysis/faithfulness_20260819_2017_mintaka_test_raw_raw.json`. |
| Grounded/ungrounded by response outcome and type-plausibility | `python tools/grounding_outcome_matrix.py $testRaw`. |
| Human validation of the faithfulness instrument | `python tools/emit_judge_validation.py $devRaw --agreement`. Reads the retained annotation sidecar and verifies its faithfulness-file hash. |
| Same-label statements and context-noise audit | `python tools/measure_context_noise.py $devRaw`. |
| Development changes and repeated-run variation | `python tools/compare_runs.py A_RAW.json B_RAW.json --metric f1`; use the exact retained files in the [development index](../data/results/dev_runs/INDEX.md). Other metrics are `hallucination`, `correct` and `abstention`. |
| Retrieval latency | `data/analysis/retrieval_latency.json` records the 40-question warm-cache measurement; timing is hardware-dependent. |

For DEV context summaries, substitute `$devDir` for both context-size input
directories. The instrument counts the entire saved context with
`len(context.split())`, including headers and bullet markers. TEST medians
are 8,856/271/35 words for C2/C3/C4; these are not the means printed by the
main outcome report.

For the gold-form change check, the tool reports both the ranked C4 fact
strings alone and the complete stored C3 context, including its header.
The latter is the thesis definition: 1,304 forms detected before condensing,
of which 264 are not detected afterwards. The fact-strings-only variant gives
1,303 and 263. The single difference is question `bb599ae9`, whose reference
form "Mitt Romney" appears in the C3 header. Neither definition establishes
that the evidence is sufficient or identifies the source of newly detected
answer text.

The context-support JSONs are original model measurements. Re-running
`score_faithfulness.py` would create a new model measurement, not reproduce a
deterministic statistic. In particular, the human validation is bound to the
retained DEV file by SHA-256 and must not be paired with a regenerated judge
pass. The stored faithfulness-contract diagnostic is retained because the
metric supplement uses it as a consistency check, not as another headline
metric.

## Denominators and comparisons

The full-test denominator is 4,000 for every configuration. An attempt means
an answer classified as correct or hallucinated; abstentions and Other are
excluded. Each configuration's attempted population is different. A paired
attempted-set comparison uses the intersection of the two configurations'
attempt sets and recomputes both values on that common set.

Faithfulness is conditional on an attempted answer with a usable stored
score. It is undefined for C1, which receives no context. Missing scores are
excluded, not assigned zero. Correctness tests agreement with Mintaka gold
answers; faithfulness tests judged support from the supplied context. The
gold-form presence check detects reference surface forms and does not prove
that the evidence is sufficient or identify the source of a generated fact.

The primary hallucination threshold is 0.5; sensitivity thresholds are
0.3 and 0.7. Bootstrap analyses use 10,000 resamples and seed 0. Binary paired
outcomes additionally use exact McNemar tests where specified. Subgroup
comparisons are exploratory, with unadjusted intervals and p-values; the
small string-answer group contains only eight test questions. The supplement's
`results.json` records cohort sizes and membership hashes alongside the
comparisons.

## Data and generation conditions

The question files preserve the typed records from the
[Amazon Science Mintaka release](https://github.com/amazon-science/mintaka):
`data/questions/mintaka_dev_raw.json` (2,000), `mintaka_test_raw.json` (4,000),
and `mintaka_sample_dev_200.json` (200). The sample was drawn from DEV with
seed 42, balanced over nine complexity classes: comparative and generic have
23 questions each and the remaining seven have 22 each. The training split
is not needed for evaluation, but is needed to recreate descriptive figures
covering all 20,000 questions. Retained data remain subject to the third-party
licence notices in the root README.

To plot the shipped test split, run `python tools/plot_mintaka_stats.py --splits test --out output/figures`.
For the optional full-dataset figures, first run
`python tools/download_mintaka.py --splits train`, then
`python tools/plot_mintaka_stats.py --splits train dev test --out output/figures_all`.
Downloading only the omitted training split preserves the frozen development
and test files. The downloader preserves all JSON record fields but rewrites
JSON formatting; it is not a byte-preserving replacement for the frozen files.

Mintaka question QIDs supply retrieval anchors; answer annotations are kept
for scoring and are not passed to the pipelines. `supportingEnt` and
`supportingNum` are retained metadata, not retrieval or prompt inputs.

Frozen corpus inputs are `data/cache/wikidata_statements/` (schema v8) and
`data/cache/wikipedia/` (schema v1). Cache records carry fingerprints and
fetch metadata; Wikipedia records include revision IDs. These are selected
entity neighbourhoods and associated articles, not whole-knowledge-base
snapshots. Live refetching may change the corpus. Use the saved caches and
the exact stored contexts for reproducing this study; the demo uses a
separate writable overlay.

The reference used `nvidia/llama-3.3-nemotron-super-49b-v1`, temperature 0,
128 answer tokens and 384 condensation tokens. Retrieval used MiniLM cosine
ranking, per-entity score normalisation followed by global top-30 selection,
the full question-entity block, statement cache v8, and 300-word Wikipedia
windows with 50-word overlap. Execution used two workers and 33 requests per
minute. Exact prompts and settings are in each run's `meta.json`; C4 adds a
condensing call before answering.

The retained `--value-desc collision` option is a development-only override
for appending descriptions to ambiguous graph values. It is `off` in the
frozen configuration and rejected by the TEST guard. No results from that
optional extension are included as thesis evidence.

The recorded NVIDIA Build endpoint was retired after the experiments. Stored
outputs remain re-scoreable, but a new generation through another endpoint
or model is a new experiment. Temperature 0 does not guarantee identical API
outputs. The demo's replacement model is labelled non-reference and is not
evidence for the thesis scores. No fresh TEST generation is needed to verify
the submitted results.

## Experiment provenance

The development programme and its exact retained runs are listed in the
[development index](../data/results/dev_runs/INDEX.md). The dated internal
protocol recorded the depth selection criterion (overall F1, ties to smaller
depth), the allocation and entity-block checks before the reference run, and
the ten prompt variants before their execution on 18–19 August. The
19 August amendment specified the grounded-by-outcome decomposition and
extended the frozen faithfulness instrument to TEST. The later detailed
dataset stratification is post-hoc. This guide summarises those records; it
does not provide an independently timestamped public registration.

Run-start commit IDs and scorer commit IDs refer to the private development
history, which is not included in this one-commit snapshot. They are retained
as provenance identifiers, not promised checkout targets. The sealed run's
raw SHA-256 and appended scoring records remain unchanged. Original run
purposes retained in `meta.json` may mention private planning files or
superseded settings. These describe historical runs, not instructions for
the current implementation.

The final package preserves the original hash-pinned evidence bytes.
An earlier public export had normalized selected files from CRLF to LF;
the submission restores their exact recorded bytes only where a complete
SHA-256 match verifies that restoration. Recorded hashes and JSON values are
not changed. Git attributes disable line-ending conversion under `data/`,
so a fresh clone preserves those evidence hashes on every platform.

During early scorer development, outputs for 100 TEST questions were
inspected. No model was trained on them, but their inclusion in the final
evaluation introduces dependence between scorer development and evaluation;
the inspected sample's 2.5% share does not bound its effect.

## Wikidata representation and historical comparison

The final C3/C4 pipeline retrieves Wikidata statement nodes, preserving
qualifiers, ranks and typed values rather than using only simplified truthy
(`wdt:`) edges. The figures below describe an earlier inspection, not a
measurement of the final v8 corpus.

The thesis's 25.3% and 31.1% figures come from a live Wikidata inspection on
11 August 2026, documented for the first 60 distinct gold QIDs encountered in
the 200-question DEV sample. The recorded counts were:

| Measurement | Count |
|---|---:|
| Full statements | 11,873 |
| Distinct truthy edges | 8,870 |
| Difference | 3,003 (25.3% of full statements) |
| Statements carrying at least one qualifier | 3,697 (31.1%) |

These counts compare statement nodes with distinct `wdt:` edges and count
statements with at least one qualifier. They motivate preserving statement
identity and qualifiers; they do not measure an answer-quality gain. The
original dated note is preserved privately, but a hash-pinned raw response
file for this live inspection was not located. The final v8 caches are a
later, filtered corpus and must not be presented as a byte-for-byte
reproduction of that earlier inspection.
